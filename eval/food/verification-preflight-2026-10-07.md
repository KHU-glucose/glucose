# 독립 재분석 실험 사전 점검

작성일: 2026-10-07
상태: 기존 기록의 예비 비교. 새 API 실험이나 운영 B 기능 구현·채택 결과가 아니다.

## 기준 문서와 실험 범위

사용자가 전달한 `food-recognition-verification-plan.md`(2026-10-06)를 기준으로 한다.
문서는 A(단일 분석)와 B(독립 재분석 + 규칙 검사 + 충돌 처리)를 비교하자는 제안이다.
두 번째 호출에는 첫 번째 답을 보여주지 않는다. 일치율을 정답률로 해석하지 않는다.
운영 API 형식, 사용자 확인 화면, 저장 기능, 백엔드의 저혈당 처치 판정을 이번 점검에서 바꾸지 않았다.

문서와 현재 코드 사이에 다음 차이가 있어 본 실험의 기준을 먼저 확정해야 한다.

| 항목 | 전달 문서 | 현재 활성 프롬프트 examples-v3 |
|---|---|---|
| 식사 개수 | 셀 수 있는 낱개만 기록, 그릇 음식은 1 | MEAL의 count는 항상 null |
| 사용자 확인 | 저장 전 확인·수정 유지 | 앞선 개선 논의는 추가 사용자 입력 없는 분석을 목표로 함. 프롬프트만으로 앱 확인 화면의 존재를 확인할 수 없음 |

권장 준비: 운영 프롬프트는 그대로 보존하고, 문서의 개수 규칙을 반영한 별도 실험용 버전을 만든다.
A와 B에 동일한 실험용 프롬프트를 사용해 재분석 효과와 프롬프트 변경 효과를 섞지 않는다.
이는 현재 운영 설정 그대로의 A와는 다르므로 보고서에서 '문서 규칙에 맞춘 단일 분석 기준'으로 명시해야 한다.
운영 설정 그대로의 A가 필요한지는 팀 확인 후 결정한다.

## 기존 기록으로 가능한 예비 비교

다음 두 기록은 동일 사진 10장, 동일 모델, 동일 프롬프트·스키마·이미지 설정이다.
각 사진의 원본 SHA-256도 일치한다. 인식 코드는 첫 답을 다음 호출에 넣지 않는다.
다만 서로 다른 시점에 실행한 단일 분석 기록을 사후 비교한 것이며,
규칙 검사와 충돌 처리를 포함하는 완전한 B 실험을 실행한 것은 아니다.
추가 API 호출이나 비용 발생 없이 비교했다.

- 첫 기록: `reports/prompt-examples-v3-20261007.json`
- 재실행 기록: `reports/prompt-examples-v3-repeat-20261007.json`
- 설정: gpt-6-luna, detail=low, 이미지 긴 변 최대 768px, 출력 최대 1200토큰.
- 정답: 기존 10장 라벨의 대표 음식 이름. 반찬 전체·개수·분류 정답은 완성되지 않았다.
- 이름 평가: 기존 정규화·별칭 기준. '만두'의 허용 별칭은 '찐만두'이며 '군만두'는 포함하지 않는다.

| 대표 음식 정답 | 첫 분석 이름 | 재실행 이름 | 이름 비교 |
|---|---|---|---|
| 갈비구이 | 닭구이 | 닭구이 | 같은 오답 반복 |
| 갈비탕 | 갈비탕 | 소고기국수 | 첫 정답과 충돌 |
| 갈치구이 | 생선구이 | 생선구이 | 같은 상위 이름 반복; 현행 구체명 정답 기준에서는 불일치 |
| 김밥 | 김밥 | 김밥, 단무지 | 대표 이름 일치; 단무지는 정답 라벨에 없어 평가 보류 |
| 김치찌개 | 김치찌개 | 김치찌개 | 대표 이름 일치 |
| 된장찌개 | 된장찌개 | 두부찌개 | 첫 정답과 충돌 |
| 만두 | 만두 | 군만두 | 첫 정답과 충돌 |
| 새우튀김 | 새우튀김 | 새우튀김 | 대표 이름 일치 |
| 식혜 | 식혜 | 식혜 | 이름 일치, 개수·단위 충돌 |
| 약과 | 시간 초과 | 약과 | 두 분석의 일치 여부 평가 불가 |

관측 결과:

- 첫 분석 대표 이름 정답은 7/10, 재실행은 5/10이다. 이는 이미 튜닝에 사용한 10장의 결과이지 최종 검증 정확도가 아니다.
- 두 번 모두 응답한 9장 중 대표 후보 이름이 공통으로 있는 사진은 6장이다.
  그중 기존 대표 음식 정답과 일치한 것은 4장(4/6, 66.7%)이다.
  이는 '공통 이름'에 대한 예비 수치로, 완전한 B의 high 정답률·전체 항목 정확도가 아니다.
- 첫 분석에서 대표 이름이 틀렸고 응답은 성공한 2장은 모두 같은 이름을 반복했다.
  이 두 사례에서는 이름 충돌만으로 오답을 발견하지 못했다. 응답 실패 1장은 오인식과 구분한다.
- 첫 분석 대표 이름이 맞았던 7장 중 3장은 다음 분석에서 다른 이름을 냈다.
  이는 원시 이름 충돌 3/7이며, 상위 분류 처리 후의 최종 '정답 불확실화율'이 아니다.
- 식혜는 첫 결과 count=null/unit=잔, 다음 결과 count=1/unit=그릇이다.
  문서대로라면 숫자를 평균 내거나 다음 값으로 덮어쓰지 않는다. 실제 개수 정답은 아직 평가하지 못한다.

결론: 같은 모델의 재분석이 같은 실수를 반복하거나 첫 정답과 충돌하는 실제 사례가 있다.
두 번 일치했다는 이유만으로 정확도가 개선됐다고 주장하거나 사용자 확인을 제거할 근거는 없다.

## 본 실험에 필요한 준비

현재 프로젝트의 한국음식 샘플은 이미지 94장이다.
폴더별 대표 음식 이름이 있지만, 기존 평가 라벨은 10장에만 있고 개수·단위·분류 정답이 없다.
총 사진 수가 충분하다는 사실만으로 문서의 구성 조건이 충족되지는 않는다.

1. 개발팀이 음식 이름·별칭, 간식 개수·단위, 분류 정답을 확정한다. 반찬까지 평가한다면 사진의 모든 항목을 라벨링한다.
2. 문서의 식사 25/간식 15/저혈당 처치 음식 20/포장 10/비음식 10 이상 구성이 충족되는지 확인하고 부족한 사진을 추가한다.
3. 튜닝용과 최종 검증용을 고정해 나눈다. 기존 10장은 최종 검증용으로 재사용하지 않는다.
4. 이름 통일 사전·상위 분류 사전과 규칙 검사를 실험 전에 고정한다. 정답을 보고 사진별 결론을 조정하지 않는다.
5. A/B 공통 프롬프트와 개수 규칙을 확정한다. context는 라벨에 실제로 제공한 값만 보내고 임의로 만들지 않는다.
6. '의미 있게 높음'의 최소 개선 폭과 평가 단위(사진/항목)를 팀이 정한다. 관측 결과를 보고 합격선을 정하지 않는다.

이후 작은 개발용 A/B 실험부터 실행해 다음을 함께 기록한다.

- 실제 정답 대비 이름·개수·단위·비음식·처치 음식 구분 성능.
- 일치 결과의 정답률과 A의 high 정답률. count=null끼리의 일치는 개수 정답으로 세지 않는다.
- 틀린 확정 비율, 미확인 비율, 첫 오답 발견율, 첫 정답 불확실화율. 각각 분모를 명시한다.
- 두 호출과 후처리를 포함한 B의 실제 전체 응답 시간.
- 두 호출 및 재시도의 비용. 성공 응답의 토큰만 합친 값을 실제 총비용이라고 부르지 않는다.

현재는 개수·처치 음식·비음식 정확도, 완전한 B의 응답 시간·비용과 채택 기준을 판정할 수 없다.
사용자 확인 제거, 운영 응답 형식 변경, 크롭·검출 모델 추가, 커밋·푸시·배포는 실행하지 않았다.

## 평가 참고

OpenAI Docs의 [평가 모범 사례](https://developers.openai.com/api/docs/guides/evaluation-best-practices)는
목표·데이터·평가 지표를 정해 비교하고, 자동 평가를 사람의 판단과 맞춰 검증하도록 안내한다.
이 점검에서도 제한된 대표 이름 라벨과 사후 비교의 한계를 명시하고 채택 판정을 보류했다.
