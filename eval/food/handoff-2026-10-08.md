## 최신 설정 변경: detail=low 복귀 + 표시용 대분류

사용자 요청으로 다시 `detail=low`로 낮추고 기본 프롬프트 `cuisine-v7`을 적용했다.
v3 원문에 음식별 `food_group`(한식/일식/중식/간식 또는 null) 지침만 덧붙였으며,
기존 음식명·개수·category_hint·768px·모델 선택·출력 토큰 규칙은 유지한다.
`name`에 접두사를 붙이지 않고 화면에서만 `한식 - 김치찌개`처럼 조합한다.
간식은 나라보다 간식 분류를 우선하고, 네 범주 밖 음식·음료·술·분류 불확실은 null이다.
ML 계약서·모델·백엔드 인식 결과 조회 DTO를 업데이트했다. 기존 응답의 누락 필드는 null로 읽는다.
intake 저장/iOS 화면 구현과 대분류 정답 채점은 범위 밖이며 실제 사진 v7 평가는 아직 하지 않았다.
스키마가 추가됐으므로 이전 71%/76%를 v7 성능으로 사용하지 않는다. 옛 결과를 덮어쓰지 않는다.
다음은 대분류 기준·정답을 검수하고 별도 실험 폴더에서 v7 음식명·대분류·시간·토큰을 평가하는 것이다.

이번 변경 검증: 음식 대분류/호출 설정 테스트 32개와 평가 도구 테스트 17개 통과.
기존 v3 원문 해시·low 요청·기존 분류 유지·옛 응답 읽기·OpenAI 필수 nullable 스키마를 확인했다.
Windows 기본 이벤트 루프에서 멈춤이 있어 테스트 프로세스에만 Selector 정책을 적용했다.
ML 전체 테스트는 메모리/페이징 파일 부족으로 수집 중 실패했다. 백엔드 신규 DTO 호환성 테스트는
Java 21 실행 환경이 없어 실행하지 못했다. 전체 통과·실제 사진 성능 향상·배포 완료를 뜻하지 않는다.

## 이전 설정 실험: 음식 인식 detail=high

사용자 요청으로 이미지 상세도만 `low` → `high`로 올렸다. 프롬프트(v3)·모델 선택·768px 제한·
출력 토큰·응답 형식은 그대로였다. 해당 평가 보고서에는 high가 기록됐다. 기존 100장 71%는
low 조건의 결과이며 원본은 보존한다. 이어서 사용자 요청으로 같은 100장의 high 평가를 완료했다.
[비교 결과](image-detail-comparison-2026-10-08.md): 이름 일치 71% → 76%, 중앙값 3.660초 → 4.4345초,
입력 토큰 147,891 → 153,194. 양쪽 유효 응답 99/100. 새 일치 8장·새 불일치 3장.
원본 9개 근거 파일은 변경되지 않았으며 새 실행은 v3-high-execution-01에 보존했다.
이후 사용자가 low 복귀와 대분류 추가를 요청했다. 현재 설정은 위 최신 항목을 따른다.

## 최신 추가 합의: 같은 음식 계열 안에서만 영양 비교

[계열 우선 평가 구현·분모·오프라인 명령](family-gated-nutrition.md)을 확인한다.
초기 5개 계열 표와 100g당 탄수화물·당류 참고값 비교를 추가했다. 자료 부족·값 누락·대응 불명확은
보류하며 다른 계열은 비교하지 않는다. 기존 운영 인식 설정·API·음식명 점수는 유지했다.
기존 100장을 API 호출 없이 별도 진단했고 원본 6개 파일의 해시가 동일했다.
음식명 71/100은 유지, 명칭 표 등록은 10/100개뿐이다. 음식명이 다른 쌍의 영양 비교는 자료 부족으로
아직 미측정이다. 다음은 사진/계열 표 검수와 떡볶이·치즈떡볶이, 김밥·참치김밥의 영양 자료 확보다.

## 다음에 이어서 할 일 — 우선순위

추가 합의: [음식명 / 혈당 관리용 특성 두 축](two-axis-accuracy.md)으로 결과를 표시한다.
현재 100장 대표 음식명은 71%, 혈당 관리용 특성은 그룹 정답이 없어 미측정이다.
새 요약 기능은 평가용 출력만 변경하며 기존 결과·정답·기본 프롬프트는 보존한다.
두 축 요약 추가 후 ML 테스트 70개와 도구 테스트 13개 통과. 기존 100장 원본 리포트를
읽기 전용으로 재집계해 음식명 71/100·그룹 미측정·원본 해시 유지도 확인했다.

1. **사람이 사진과 정답을 검수한다.** 개발용 불일치부터 명칭 범위 차이, 원본 라벨 오류,
   실제 인식 혼동을 구분하고 일치 사진도 일부 검수한다. 대표 클래스 라벨은 사진 전체 정답이 아니다.
   한식 사진에서는 계란찜/죽, 삼계탕/닭곰탕, 식혜/막걸리 등의 사례를 우선 확인한다.
2. **음식명·개수 채점 기준을 고정한다.** 식사류는 대표 음식명을 평가하고 count=null,
   간식류는 명확히 보이는 낱개·조각·포장 수만 정답을 작성한다. 숨은 재료나 전체 양을 추측하지 않는다.
   동의어·하위 이름의 인정 기준은 결과를 보기 전에 정한다. 기존 71% 기록은 수정하지 않는다.
3. **프롬프트 비교 실험을 한다.** 한식 혼동, 근거 없는 재료 추측, 여러 음식의 항목 합치기를
   개선 대상으로 삼는다. 새 후보와 v3를 동일 개발 사진·정답·모델·이미지 설정으로 비교한다.
   후보를 바꿀 때마다 원문·해시·변경 이유·결과를 남기며 한 번의 좋은 결과로 승자를 정하지 않는다.
4. **계약서 조건의 테스트셋을 보충한다.** 한식 식사 25, 간식 15, 처치 음식 20,
   포장 제품 10, 비음식 10 이상을 포함하고 사진 전체 음식·개수·분류를 사람이 주석 처리한다.
   아직 사용하지 않은 사진을 최종 검증용으로 별도 보존한다. 이번 예약용 50장은 이미 평가했으므로
   이후 미사용 최종 검증셋이라고 부르지 않는다.
5. **혈당 관리 지표를 별도로 검증한다.** 중요 음식 누락·조리법·제품 구분의 정답과
   그룹 정책을 검토한다. 이름이 비슷하다는 이유로 영양 동등이나 같은 혈당 반응을 인정하지 않는다.
6. **응답 시간·비용·안정성을 계측한다.** 순수 스키마 실패와 API 실패를 구분하고 재시도·실패까지
   포함한 비용을 확인한다. detail/픽셀 제한 변경은 프롬프트 실험과 분리해서 비교한다.

실제 리브레 이미지와 같은 날 LibreView CSV를 비교하는 그래프 파싱 검증은 여전히 별도 과제다.
이번 음식 예비평가로 그래프 기능의 정확도를 입증하지 않았다.
