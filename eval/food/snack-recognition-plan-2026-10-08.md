# 음식 인식 개선 계획 — 간식·저혈당 처치 음식 우선 (2026-10-08)

작성: Dave(+Claude Code). 대상: ml-service 담당 팀원.
선행 문서: [v3 예비평가 결과](v3-primary-results-2026-10-08.md), [작업 인계](handoff-2026-10-08.md),
[자동분석 개선안](../../음식_사진_자동분석_개선안.md).

## 1. 우선순위 (Dave 결정)

1. **응답 시간 중앙값 3초 이내가 최우선이다.** (계약서 목표, 현재 실측 3.66초)
2. **간식, 특히 저혈당 처치 음식의 이름·개수 정확도**를 높인다.
   이름과 개수가 맞아야 백엔드가 `food_catalog`로 당류를 계산한다(이름+개수 → 당류 g, 코드 계산).
3. **식사(MEAL)는 세부 요리명이 필요 없다.** "한식"처럼 대분류로 뭉뚱그려도 된다. 개수는 지금처럼 null.

따라서 한식 요리명 인식률(현재 24/40)은 더 이상 개선 목표가 아니다.

## 2. 현재 상태에서 짚을 점

- v3 예비평가는 **간식 개수와 저혈당 처치 음식 구분을 측정하지 않았다.** 정작 중요한 부분이 비어 있다.
- 기존 프롬프트 비교(v1~v5)는 10장 기준이었고 같은 v3가 7/10 → 5/10으로 흔들렸다.
  작은 표본에서는 변화가 잡음과 구분되지 않는다(40장이면 95% 신뢰구간 약 ±15%p).
- `food_catalog` 시드가 17개뿐이라, 이름을 맞혀도 catalog에 없으면 당류 계산이 안 된다.
- 장당 입력 약 1,500토큰(대부분 프롬프트 글자), 출력 약 280토큰. 비용은 실측 약 $0.0003/장으로
  목표($0.003)의 1/10 수준이라 여유가 크지만, **응답 시간은 이미 목표를 넘었다.**
- 이미지 처리: 앱 1600px → 서버 768px(`ml-service/main.py` `MAX_IMAGE_EDGE`) → `detail=low`
  (`food_recognizer.py` `IMAGE_DETAIL`). 모델·해상도·detail은 아직 한 번도 바꿔서 비교하지 않았다.

## 3. 단계별 계획

| 순서 | 할 일 | 목적 | 담당 |
| --- | --- | --- | --- |
| 0 | **간식·처치 음식 테스트셋 직접 촬영** (아래 4절) | 공개 데이터셋엔 이런 사진도 개수 정답도 없다 | 팀 |
| 1 | **응답 시간 분해 측정**: 모델 응답 / 이미지 처리 / 재시도. 중앙값과 느린 10%(p90) 함께 | 3초 목표의 기준선 | 팀원 |
| 2 | **식사 단순화**: MEAL은 대분류 이름만(5절 결정 필요), count=null 유지 | 출력이 줄어 응답이 빨라짐 | 팀원 (계약 문서 먼저) |
| 3 | **프롬프트 축소**: 식사 이름 규칙을 빼고, 바뀌지 않는 부분을 앞에 둬서 API가 지원하면 프롬프트 캐싱이 되게 함. usage의 캐시 토큰 수로 확인 | 속도·비용 감소 | 팀원 |
| 4 | **처치 음식 표준 목록**: 20개 안팎의 표준 이름을 프롬프트에 넣고 "목록에 있으면 목록의 이름 그대로" 쓰게 함. 같은 목록으로 `food_catalog` 확장(1개당 당류, 단위 기준) | 이름이 catalog와 정확히 맞아야 당류 계산 가능. **간식 정확도의 핵심** | 팀원 + Dave(catalog) |
| 5 | **포장 라벨·개수 검증**: 포장 제품은 제품명으로 품목 판별. 개수는 경계가 확실한 것만, 애매하면 null(v3 규칙) | 개수 정확도 | 팀원 |
| 6 | **간식일 때만 해상도 올리기**: 앱이 보내는 촬영 상황(SNACK, HYPO_TREATMENT)일 때만 해상도/detail을 올려 비교. **3초 안에 들어오면 채택** | 작은 사탕 개수·라벨 읽기 | 팀원 |
| 7 | **실사용 측정**: 인식 결과(job.result)와 사용자가 수정 화면에서 고쳐 저장한 이름·개수를 비교하는 집계. 사진은 쓰지 않음 | 실제 사용자 기준 정확도, 추가 라벨링 불필요 | Dave(백엔드) |

**보류**: 독립 재분석(2회 분석)은 3초 제약 안에 넣기 어려워 보류한다. 한식 혼동쌍 보강, 한식 대표명 사전도 이제 불필요.

## 4. 테스트셋 (0단계)

- 처치 음식 15~20개 품목: 포도당 캔디, 사탕, 젤리, 초콜릿, 주스(팩·병), 탄산음료 등.
  실제로 쓰는 제품 위주로 4단계 표준 목록과 같은 품목을 쓴다.
- 품목별 개수 1~5개, 배치(흩어짐·겹침), 포장 상태(포장째·개봉)를 바꿔가며 총 150장 안팎.
- 정답: **표준 이름 + 개수 + 단위.** 가려져서 셀 수 없는 사진은 정답 개수 null.
- 식사 사진과 비음식 사진을 조금 섞어 분류 오류도 측정한다.
- 개발용과 최종 검증용을 촬영 시점에 나눠 둔다. 최종 검증용은 개선이 끝날 때까지 쓰지 않는다.
- 사진·정답은 기존처럼 `food_testing/`에만 두고 Git에 올리지 않는다.

## 5. 결정 필요

1. 식사 이름을 **"한식" 하나**로 할지, **한식/양식/중식/일식/분식** 정도로 나눌지 (Dave).
   기록 목록에 이 이름이 그대로 보인다.
2. MEAL의 `name` 의미가 바뀌므로 `docs/ml-service-contract.md`를 먼저 고치고 합의한다.
3. 처치 음식 표준 목록의 품목 (팀원이 초안 → Dave 확인 후 catalog 반영).

## 6. 진행 원칙 (기존 인계 문서와 동일)

- 한 번에 하나만 바꾼다. 같은 사진끼리 짝지어 비교하고, 채점 기준은 결과를 보기 전에 고정한다.
