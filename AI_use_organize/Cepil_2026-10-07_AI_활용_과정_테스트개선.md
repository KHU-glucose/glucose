## AI 활용을 통해 반영한 작업 내용

1. 기존 프롬프트를 `baseline-v1`로 보존하고, 상세 규칙안 `rules-v2`와 간결한 규칙·예시안 `examples-v3`를 작성했다.
2. 식사류는 이름만 분류하고 개수는 null, 간식은 보이는 낱개·조각·포장만 세도록 지시했다. 기존 응답 스키마는 변경하지 않았다.
3. 요리 속 재료의 중복 등록, 보이지 않는 개수 추정, 포장 글자 추측을 제한했다. 사진만으로 실제 섭취 여부를 판단하지 않도록 했다.
4. 기존 모델, detail=low, 긴 변 최대 768px, 출력 상한 1200토큰, 요청별 타임아웃·재시도 설정을 유지했다.
5. 평가 도구에 버전 선택, 프롬프트 원문·설정·해시 기록, 간식 개수와 계약상 FAST_SUGAR 지표, 미측정·데이터 부족 판정을 추가했다.
6. `make eval` 실행 경로와 Windows용 동등 명령을 문서화했다. 사진·비밀키·개인 경로를 제외한 실제 응답 비교 증빙을 저장했다.

## 프롬프트와 반영 결과

### 참가자의 요구 — 원문

```text
완료 기준이랑 평가 방법 읽어봐. 일단 프롬프트를 최대한 좋게 정제하는걸로 성능 올려보자.
그리고 그 과정도 제출해서 보여주면 좋겠어
```

반영 결과: 계약서의 목표 수치를 기준으로 비교 실험을 수행하고, 좋은 결과뿐 아니라 실패한 개선안도 보존했다.

### 참가자의 기능 정책 — 이전 대화 요약

```text
사용자는 앱을 직접 열거나 음식 정보를 추가 입력하지 않고 사진 한 장으로 등록할 수 있어야 한다.
간식류는 개수를 구분하고, 식사류는 음식이 무엇인지만 분류한다.
detail=low는 토큰을 아끼기 위한 시험 설정이므로 이번에는 유지한다.
```

반영 결과: 사용자 입력 요구 없이 서버의 고정 프롬프트를 개선했다. 추가 API 재검토나 화질·모델 변경은 이번 실험에 넣지 않았다.

### 서버 분석 지시 — 실제 원문 발췌

기존안:

```text
count는 낱개 수를 신뢰성 있게 셀 수 있을 때만 정수로 씁니다.
그릇 음식은 한 그릇이면 1이고, 셀 수 없으면 null입니다.
```

3차안:

```text
name은 한국어로 일상에서 쓰는 대표 요리명입니다. 브랜드나 임의의 원재료 나열을 이름으로 쓰지 않습니다.
전체 형태와 조리 방식, 국물, 주재료를 함께 보고 가장 잘 맞는 요리명을 고릅니다.
MEAL은 이름만 분류하고 count=null입니다.
SNACK과 낱개 FAST_SUGAR는 확실히 셀 수 있는 전체 개수만 기록합니다.
likely_consumed_all은 항상 null입니다.
```

원문 전체는 [프롬프트 코드](../ml-service/food_prompts.py)에 버전별로 보존했다.
쿠키·사탕·볶음밥의 짧은 예시는 출력 정책 설명이며, 정답 사진을 제공한 few-shot 이미지 학습이 아니다.
평가 대상 사진의 정답을 모델에 전달하지 않았다.

## 오류 분석 및 개선 판단

- 상세 규칙안은 기존보다 점수가 낮았다. 규칙을 많이 적는 것만으로 성능이 향상되지 않았다는 실제 실패 결과다.
- 긴 지시, 보수적인 상위 이름 선택, 세부 조리명 선택 등이 영향을 줬을 가능성은 있지만 여러 요소를 함께 바꿨고 한 번씩만 실행했으므로 원인을 확정할 수 없다.
- 3차안은 개발용 이름 점수가 10%p 높았지만, 이는 10장에서 단 한 개 차이다. 모델 응답 변동과 표본 규모 때문에 일반 성능 향상으로 단정하지 않는다.
- 시간 초과가 2차·3차에서 각각 한 번 있었다. 3차가 모든 면에서 더 좋다고 주장하지 않는다.
- 모든 버전에서 갈비구이의 육류 종류와 갈치구이의 구체적인 생선 이름은 해결되지 않았다.
- 3차의 성공 응답에서 MEAL 개수는 모두 null이었다. 이는 이 표본에서의 정책 준수 확인이지 간식 개수 정확도 검증이 아니다.
- 김밥 사진에는 실제 단무지가 있으나 정답에 주된 음식만 적혀 있다. 3차가 단무지를 덜 반환했다고 정확도가 높아졌다고 주장할 수 없다.
  원본 정밀도/F1은 각각 54.55%/0.5714, 30%/0.3, 77.78%/0.7368이지만 완전한 라벨에 대한 성능 수치로 사용하지 않는다.
- 현재 코드 기본값은 `examples-v3`인 추가 검증용 후보이다. 서버 배포나 최종 성능 승인까지 완료했다는 뜻이 아니다.

## 추가 실험 — 음식명 지시만 바꾼 후보와 반복 검증

참가자 요청 원문:

```text
더 프롬프트 갈고 닦아봐
```

### 변경 가설과 통제 조건

이번에는 3차안의 음식명 선택 문단만 변경했다. 분류, 식사 개수 null, 간식 단위,
포장 글자, 섭취 여부, 출력 스키마 및 모델·화질·재시도 설정은 유지했다.

- `focused-v4`: 완성 요리명과 재료 나열의 차이를 더 명확히 하고, 전체 형태·질감·국물·주재료가 함께 뒷받침하는 이름을 고르도록 문단을 교체했다.
- `contrast-v5`: 3차안에 윤곽·뼈·껍질·질감·국물·면·곡물 등의 구별 단서를 추가했다. 색·접시·배경 하나만으로 종류를 확정하지 않도록 했다.
- 특정 평가 사진의 정답 이름을 추가하거나 허용 동의어를 늘리지 않았다. 다만 같은 개발용 데이터를 반복 참고했으므로 데이터에 대한 과적합 가능성은 남는다.
- 4차·5차를 먼저 한 번씩 실행하고, 이름 점수가 같을 때 최종 정상 응답률을 우선해 4차를 반복 후보로 선정했다.
- 기존 3차와 후보 4차를 각각 한 번 더 실행했다. 이번에는 총 40개 평가 요청을 추가했으며 SDK·애플리케이션의 오류 재시도는 별도 발생할 수 있다.

| --- | --- | --- | --- | --- |
| 3차 | 2회 | 12/20, 60% | 19/20, 95% | 4.4275초 |
| 4차 | 2회 | 11/20, 55% | 19/20, 95% | 3.8445초 |
| 5차 | 1회 | 7/10, 70% | 9/10, 90% | 4.3575초 |

20번 시도는 서로 다른 사진 20장이 아니라 같은 사진 10장을 두 번 분석한 것이다.
합산 중앙값은 각 회차 중앙값의 평균이 아니라 모든 개별 요청 시간을 합쳐 다시 계산했다.
5차는 한 번만 실행했으므로 두 번 실행한 버전과 안정성을 동등하게 비교할 수 없다.
정답·스키마·원본 사진 해시가 모든 실행에서 같은 것을 확인했다.

### 분석과 채택 판단

- 4차의 첫 실행에서는 약과를 맞혔지만 만두를 군만두로 답했다. 반복에서는 갈치구이를 고등어구이, 식혜를 쌀죽으로 답했고 약과는 시간 초과였다.
- 3차도 반복에서 갈비탕을 소고기국수, 된장찌개를 두부찌개, 만두를 군만두로 답했다. 모델 결과가 프롬프트를 유지해도 변동하는 것을 관찰했다.
- 4차의 속도 중앙값은 낮았으나 이름 점수가 개선되지 않았고 3초 목표에도 못 미쳤다. 따라서 4차를 기본값으로 교체하지 않았다.
- 5차의 단일 실행 70%를 더 좋은 성능의 증거로 채택하지 않았다. 같은 표본에 추가로 문구를 계속 맞춰 고치는 접근은 중단했다.
- 기본값은 `examples-v3`이다. 이것이 최적 또는 완료된 성능이라는 뜻은 아니며, 추가 후보는 버전별 실험안으로 남겼다.
- 보존한 다섯 실행의 성공 응답에서 MEAL 개수 정책 위반은 없었다. 간식 개수·처치 분류·비음식 정확도는 여전히 정답 부족으로 미측정이다.
- 단무지는 불완전한 정답 라벨 때문에 정밀도 해석이 제한된다. 단무지 반환을 줄이는 방향으로 점수를 인위적으로 올리지 않았다.

### 추가 검증과 증빙

- 서비스 테스트: `32 passed`. 새 후보의 실제 전달값과 기존 v3 프롬프트 해시 보존을 추가로 확인했다.
- [추가 실험 및 반복 결과 JSON](../eval/food/evidence/prompt-refinement-2026-10-07.json): 프롬프트 원문·각 응답·오류·시간·토큰·합산 지표를 포함하고 이미지 원본·개인 경로·비밀키는 제외했다.
- 실행 순서 및 파일: 4차 첫 실행 → 5차 첫 실행 → 3차 반복 → 4차 반복. 원본은 `eval/food/reports/prompt-focused-v4-20261007.json`, `prompt-contrast-v5-20261007.json`, `prompt-examples-v3-repeat-20261007.json`, `prompt-focused-v4-repeat-20261007.json`에 보존했다.
- [OpenAI Reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices)의 간결한 지시 원칙을 참고했고, 장문의 사고 과정 출력을 요구하지 않았다. 효과는 문서의 일반 조언이 아닌 실제 평가로 판단했다.

결론: 프롬프트를 추가 정제했지만 이번 변경으로 정확도가 더 올랐다는 증거는 얻지 못했다.
최종 성능을 개선·검증하려면 모든 보이는 음식과 간식 개수 정답을 확정한 별도 사진과 반복 평가가 필요하다.
모델이나 detail 설정을 변경한 실험은 이번에 수행하지 않았으며, 외부 제출·배포·커밋·푸시도 하지 않았다.
