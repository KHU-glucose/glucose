# AI 활용 과정 기록 공통 규칙

이 폴더는 경진대회 제출을 위해 팀원별 AI 활용 과정과 실질적인 기여 내역을 기록하는 공간이다.

전체 대화 내용을 무조건 제출하지 않고, 심사위원이 다음 내용을 확인할 수 있도록 핵심 증빙만 선별해 작성한다.

- 어떤 작업에 어떤 AI를 사용했는가
- 어떤 핵심 프롬프트를 사용했는가
- 프롬프트를 통해 결과물이 어떻게 바뀌었는가
- 참가자가 직접 판단하고 수행한 작업은 무엇인가
- 결과를 어떤 방법으로 검증했는가

## 1. 파일명 규칙

모든 개인 기록 파일은 다음 형식을 사용한다.

```text
GitHubID_YYYY-MM-DD_AI_활용_과정_작업한부문.md
```

예시:

```text
Cepil_2026-10-05_AI_활용_과정_제작개발.md
honggildong_2026-10-06_AI_활용_과정_테스트개선.md
```

### 파일명 작성 원칙

- `GitHubID`: 작성자의 실제 GitHub 아이디를 사용한다.
- 날짜: `YYYY-MM-DD` 형식으로 작성한다.
- `작업한부문`: 공백과 특수문자를 피하고 간결하게 작성한다.
- 권장 부문명:
  - `문제정의`
  - `자료준비`
  - `기획설계`
  - `제작개발`
  - `테스트개선`
  - `최종결과물`
- 같은 날 서로 다른 부문을 수행했다면 파일을 분리하거나 `제작개발_테스트개선`처럼 함께 표시할 수 있다.

## 2. 작성 범위 원칙

- **실제로 수행한 단계만 작성한다.**
- 수행하지 않은 `문제 정의`, `자료 준비` 등의 단계를 억지로 채우지 않는다.
- 한 파일에는 해당 날짜와 해당 작업 부문에서 수행한 내용만 기록한다.
- AI가 제안한 내용과 참가자가 직접 결정·수행한 내용을 구분한다.
- 결과만 적지 말고 핵심 프롬프트와 변경 과정을 함께 남긴다.

## 3. AI 모델 작성 원칙

가능한 범위에서 서비스명, 모델명, 사용 목적을 함께 작성한다.

예시:

```text
OpenAI Codex: 코드 작성 방법 설명 및 오류 분석
OpenAI GPT-6 Luna: 음식 이미지 분석 API 실행 모델
```

모델명을 정확히 확인할 수 없다면 임의로 추측하지 말고, 확인 가능한 서비스명과 화면에 표시된 모델명만 기록한다.

## 4. 주요 프롬프트 작성 원칙

- 전체 대화를 복사하지 않고 결과물에 영향을 준 핵심 프롬프트만 선별한다.
- 실제 문장을 그대로 적었다면 `원문`이라고 표시한다.
- 여러 대화를 하나로 정리했다면 `요약` 또는 `대표 프롬프트`라고 표시한다.
- 단순 질문보다 요구사항 결정, 코드 변화, 오류 해결에 영향을 준 프롬프트를 우선한다.
- 각 프롬프트가 어떤 변경으로 이어졌는지 추적할 수 있게 작성한다.

좋은 예시:

```text
[대표 프롬프트]
“사진에 음식이 여러 개라면 각 음식을 배열로 구분하고,
탄수화물·단백질·지방·당류와 전체 합계를 JSON으로 반환하고 싶다.”

[반영 결과]
FoodItem 배열과 네 가지 영양소 필드가 추가되었다.
```

## 5. 필수 작성 항목

모든 기록은 [`TEMPLATE.md`](./TEMPLATE.md)를 복사해 작성하며, 다음 항목을 반드시 포함한다.

1. 작성자, 날짜, 작업 부문, 담당 기능
2. 사용한 AI 모델과 사용 목적
3. 핵심 프롬프트
4. AI 활용을 통해 반영된 작업 내용
5. 참가자가 직접 수행한 실질적 기여
6. 테스트 또는 검증 방법과 결과
7. 코드·문서·커밋 등 증빙 위치
8. 개인정보 및 비밀정보 제거 확인

다음 항목은 해당되는 경우에만 작성한다.

- 프롬프트에 따른 버전 변화
- 오류 분석과 개선 과정
- 실패한 접근과 변경 이유

## 6. 참가자 기여 작성 원칙

AI가 모든 작업을 수행한 것처럼 기록하지 않는다. 참가자가 실제로 수행한 다음 활동을 구체적으로 작성한다.

- 요구사항 결정
- AI 답변 검토 및 선택
- 코드 직접 입력·수정
- 실행 및 테스트
- 오류 로그 확인
- 결과 비교와 판단
- 팀 공유와 형상 관리

예시:

```text
AI가 제안한 예외 처리 코드를 참가자가 직접 반영하고,
Swagger에서 정상 이미지·비음식 이미지·잘못된 파일을 각각 테스트했다.
```

## 7. 검증 및 증빙 원칙

- 프롬프트만 제출하지 말고 결과가 실제로 반영되었음을 보여주는 증빙을 남긴다.
- 권장 증빙:
  - 핵심 코드 변경 전후
  - Swagger 또는 앱 실행 결과
  - 오류 로그와 수정 후 성공 결과
  - Git 커밋 또는 Pull Request
  - 결과 비교표
- Markdown에는 저장소 내부 상대 경로를 사용해 결과물을 연결한다.
- 이미지 증빙이 필요하면 API 키, 이메일, 사용자 경로 등 개인정보를 가린다.

## 8. 보안 및 개인정보 규칙

다음 내용은 문서, 스크린샷, Git 기록에 절대 포함하지 않는다.

- OpenAI API 키와 기타 서비스 비밀키
- `.env` 파일 내용
- 비밀번호와 인증 토큰
- 개인 이메일, 전화번호 등 불필요한 개인정보
- 사용자 홈 디렉터리 등 제출에 필요하지 않은 로컬 경로
- 실제 의료 개인정보 또는 식별 가능한 사용자 데이터

키가 노출되었다면 문서에서 가리는 것만으로 끝내지 않고 즉시 폐기한 뒤 새 키를 발급한다.

## 9. 작성 방법

프로젝트 최상위 폴더에서 템플릿을 복사한다.

```powershell
Copy-Item `
  .\AI_use_organize\TEMPLATE.md `
  .\AI_use_organize\GitHubID_YYYY-MM-DD_AI_활용_과정_작업한부문.md
```

파일명을 자신의 정보에 맞게 바꾼 뒤 템플릿의 안내 문구와 예시를 실제 내용으로 교체한다.

## 10. 커밋 전 확인

- [ ] 파일명이 공통 규칙을 따르는가?
- [ ] 실제로 수행한 단계만 작성했는가?
- [ ] AI 모델과 사용 목적을 적었는가?
- [ ] 핵심 프롬프트와 반영 결과가 연결되는가?
- [ ] 참가자의 직접 기여가 구체적으로 적혀 있는가?
- [ ] 테스트 또는 검증 결과가 있는가?
- [ ] API 키와 개인정보가 제거되었는가?
- [ ] 증빙 파일과 링크가 실제로 존재하는가?

해당 기록 파일만 스테이징하려면 다음 형식을 사용한다.

```powershell
git add -- .\AI_use_organize\GitHubID_YYYY-MM-DD_AI_활용_과정_작업한부문.md
```
